# 過去の良い例と悪い例（共通資料）

全部署が着手前に読む。制作物のレビュー（tester/critic/proofreader）や実際の公開後の気づきをここに蓄積していく。新しいエントリは末尾に追記（上書きしない）。

## 悪い例

| 日付 | 何が起きたか | 教訓 |
|---|---|---|
| 2026-08-22 | 校閲で本文に簡体字（誤字）が混入していたのを発見 | 本文執筆後は文字化け・誤変換・簡体字混入がないか機械的に確認する |
| 2026-08-22 | 出典のない具体的な数字（作業時間の具体的な分数、LINEスタンプ申請枚数の未検証な数値）を本文に書いてしまった | 具体的な数字は必ず`使用可能な実績.md`にあるものだけを使う。裏付けのない「もっともらしい数字」を書かない |
| 2026-08-22（それ以前の運用） | ペイウォール区切りに説明文付き3行ブロック（「▼ここから先は…」）を使い、下書きをそのままnoteに貼り付けると説明文が本文に残ってしまう構成だった | 「そのまま投稿する」運用を前提に、区切りは線のみ・説明文なしにする |

## 良い例

| 日付 | 何が良かったか | 再現ポイント |
|---|---|---|
| 2026-08-22 | Testimony/証拠章をプレースホルダーとしても入れず、構成そのものから外す判断をした | 「事実がないなら書かない」を、個別の文言修正ではなく構成レベルで徹底する |
| 2026-08-22 | 価格を¥1,980/¥1,480→¥500固定に変更した際、CLAUDE.md・エージェント定義・既存3記事の本文・進行キュー・出力ファイルまで一括で整合を取った | 方針変更時は「どこに古い数字が残っているか」を`Grep`等で横断的に洗い出してから直す |
| 2026-08-22 | 早割（タイムセール）を廃止する際、単に値下げをやめるだけでなく「なぜ廃止するか」（放置運用との相性、景品表示法対応の手間）を明文化した | 方針変更の理由を記録に残すことで、後で同じ議論を繰り返さずに済む |
